# MatterLoom texture pipeline

MatterLoom presents the material specialists as one texture pipeline. Its goal is a highly detailed, visually pleasing texture that passes practical sanity checks. Professionally artist-authored 16-bit diffuse, height, roughness and normal maps are the clean training targets.

Developer training starts in **Loom Room** with a bare source folder such as `/opt/ipde/sources_mats`. Add images and folders, inspect originals, edit image tags and rename material folders inside the app. Opening the folder requires no JSON or model setup and does not hash every image. New folders use a 2048 training grid; smaller originals remain visible separately from exact training crops. Teach and export the diffuse classifier in Create ML, train the category's height, roughness and normal models, then compare and approve their results. See the [source-folder guide](source-folder-workflow.md). The separate non-developer LoRA workflow is deferred.

## Implemented controls

- Fresh compact models offer widths 16, 22, 32, 46 and 64. RGB-to-scalar parameter counts are 256,257; 478,017; 999,937; 2,050,497; and 3,949,569. Normals and the one-channel DepthPro refiner show their own exact counts. Resumed models inherit their recorded width.
- Adam, AdamW and Lion are available. AdamW stays the default. Lion keeps one momentum value per parameter and uses sign updates; the UI provides an explicit lower-learning-rate setup. Follow the [original Lion implementation](https://github.com/google/automl/tree/master/lion) when tuning its smaller learning rate and larger weight decay. Fewer state values do not guarantee better texture quality.
- Adding sources copies exact original bytes and keeps material families, resolution tiers and original parent folders separate. Filename and saved-tag roles distinguish diffuse from AO and surface targets. Full verification and crop preparation occur when requested for training; crops preserve native alignment and 16-bit codes without scaling.
- Hugging Face destinations use the checkpoint's model name, map target and checksum. Model cards describe the recorded subjects, architecture, training grid, optimizer, learning-rate schedule, augmentation and map counts. For example, a named Pine Bark Height checkpoint becomes a MatterLoom surface-height / displacement specialist for Pine Bark.

## Learned photo preparation and final restoration

The artist-prepared maps support training a restoration model with controlled degradations of a clean target: noise, compression, known lighting fields and deliberately damaged seams. Generate degradations in memory, keep the original 16-bit maps intact, save the corruption recipe and seed, and keep all versions of the same material in one split. This is a useful starting point for a detailer; its validation must distinguish synthetic defects from real generated-map errors.

Photo-to-diffuse should be a separate RGB-to-RGB family. Render the artist-authored diffuse, height/normal and roughness maps under varied lighting to generate photo-like inputs paired with their clean diffuse targets. Add explicit camera-style blur, noise and compression to those generated inputs. This provides training pairs without requiring the original camera photographs: [single-image SVBRDF research](https://arxiv.org/abs/1810.09718) demonstrated training from artist-created materials rendered under varied illumination, with a loss that compares predicted and target material renderings. Real photo/finished-diffuse pairs remain useful additional validation when available.

Preserve alignment and apply the same crop to both sides. Store the rendering/degradation recipe, seed and masks; hold out entire material families. Identity training on a clean diffuse image cannot demonstrate photo shadow or noise removal. [Real-ESRGAN](https://arxiv.org/abs/2107.10833) provides a separate precedent for restoring detail using synthetic degradations; it does not by itself validate our texture pipeline.

A final material detailer should see the generated diffuse, height, roughness and normals together, with the original authored maps as targets. Use outputs generated by a model that did not train on that validation subject. Train bounded residual edits so the stage can sharpen useful features, reduce defects and improve map consistency. Keep strength adjustable and show before/after views. Separate seam repair from ordinary detail enhancement; a tiling stage should deliberately work across the wrap boundary.

These photo/restoration stages are a training design, not available trained models in this change. Existing registered companion-view fusion and editable broad-lighting correction remain available. The new compact presets let us investigate the quality/size tradeoff without changing checkpoint architecture mid-run.

## Comparison and sanity checks

For a meaningful size comparison, use the same material split, crop grid, seed, augmentation, training budget and optimizer settings for the 0.48M, 1M and 2.05M runs. Record update count, elapsed time, peak memory, file size and loss. Compare against the authored target at native zoom and in the same rendered lighting. Repeat initialization seeds before drawing a quality conclusion.

Review sharp fine detail, attractive material appearance, relief without unwanted spikes, useful roughness contrast, sane normal lengths and directions, consistency between height and normals, and seams in a repeated material. Include both numerical checks and human approval. A single successful optimizer update proves execution, not texture quality. Known-material diagnostic crops and unseen-material validation answer different questions; retain both.

## Lens correction

Use lens correction when the decoder exposes a supported, image-bound correction and it improves the result. Generic camera/lens names and focal length do not supply a distortion transform. Avoid applying another guessed warp to an already processed photo. Apple exposes explicit correction support for [CIRAWFilter](https://developer.apple.com/documentation/coreimage/cirawfilter/islenscorrectionsupported) and image/depth-bound radial tables in [AVCameraCalibrationData](https://developer.apple.com/documentation/avfoundation/avcameracalibrationdata/lensdistortionlookuptable). The current generic HEIF importer does not establish such an image-bound correction contract, so this change retains the editable manual control. This is a quality and duplicate-processing decision; camera reconstruction is not the objective.
